# Decisions

One file per decision that would otherwise be re-argued: `NNNN-short-title.md`.

A decision record says what was decided, what it rules out, and what would make
it worth revisiting. It is written once and not edited afterwards — a decision
that changed is a new record that supersedes the old one, because the point of
the file is the reasoning available at the time.

The template is `0000-template.md`.

The decisions OpenADLC was built on so far are the D-table in
[platform-plan.md](../platform-plan.md#12-decisions), one row each. A decision
taken from here on is a record in this folder; the plan's table links to one
only where it changed a decision the table already had (0003, from D5 and D12;
0004, from D7). The records:

- [0002](0002-design-memory.md): the design stage remembers, in ADRs and a summary of them
- [0003](0003-per-task-containers.md): a computer per task, and several tasks per seat

- [0005](0005-ruleset-bypass-is-the-app-or-a-person.md): a ruleset bypass is OpenADLC's app or a person who is not a crew account
- [0006](0006-abandoned-is-a-label.md): an issue closed without merging is Done, labelled `openadlc:abandoned`, and not shipped
- [0007](0007-self-update-follows-verified-releases.md): self-update takes only verified releases, prepared beside the install, and the checkout stays the install
- [0008](0008-a-close-stops-the-tasks-paused-on-it.md): a close stops every task paused on the issue or its pull request, at the close only, and a person's Stop ends a task waiting on a question
- [0009](0009-work-items.md): every issue, pull request and request gets a work item number of the install's own, never reused, numbered in opened order from history and linked automatically
- [0010](0010-console-name-and-logo.md): the console's name and logo are two settings, the logo a checked data URL kept out of every request's read, read by every role and drawn only through `<img>`, served sandboxed
- [0011](0011-a-request-is-answered-once-saved.md): a console request is answered once it is saved, with a prediction (`starting`, or its place in line), and its triage starts after; a failed start is said on its thread
- [0012](0012-a-request-files-one-issue-per-repository.md): a console request files one issue per managed repository it concerns, recorded in `request_issues`; an issue joins it only while its triage runs, and its triage signs for the managed repository it posts to, only on its request's issues
- [0013](0013-dependencies-across-repositories.md): a dependency may name an issue in another managed repository as `owner/name#N`; `parseDependencyRefs` replaced `parseDependencies`, one outside the install never ships, and stacking stays same-repository
- [0014](0014-the-bots-image-is-stamped-with-its-recipe.md): the bots' image carries `openadlc.recipe`, the digest of the files it is built from; an image behind its recipe is rebuilt with the versions it has, and the bridge starts that run once per recipe
- [0015](0015-a-wait-on-a-person-is-recorded-where-the-gate-is-settled.md): what the review gate waits on reaches Needs you as an event recorded where the gate is settled, once per head (`review.person_asked_again`, `review.person_awaited`), and is never read live from GitHub by the attention read
- [0016](0016-a-refused-signature-is-an-event.md): a stamp the bridge refuses is an `attribution.stamp_refused` event, matched to the unsigned post by repository, login, number and body hash; such a post is `unsigned-refused`'s, never the account's "This was me" card, and clears when a task of the same kind and subject type signs again (`attribution.stamp_signed`); a `repo@sha` task signs on the pull requests from its own branch
- [0017](0017-intake-ends-with-its-labels.md): an issue leaves intake only with its `priority:`, `area:` and one `do:` label, checked by `missingLabels` when intake's stage label comes in and when its task ends; a retry for a missing one counts toward intake's tries
- [0018](0018-a-sign-off-is-posted-with-a-token-kept-for-one-post.md): a reviewer-only pull-request command is posted with a device-flow token held for that one post and revoked; a person's GitHub account is proved by their own sign-in and kept as a login and an id; a command anyone may send is posted as the app
- [0019](0019-a-merge-of-the-base-stands-on-its-parents-local-ci.md): a crew head with no local run of its own that GitHub committed as a two-parent merge of the base into a head whose newest run passed (walked back through up to five such merges) stands on that run in the lead's `local-ci.md`; no row is written to `local_ci_runs` for it, and it is told by the commit's shape, not by `merge_line.branch_updated`
- [0020](0020-an-ignored-dependency-counts-once-closed-as-completed.md): a dependency labelled `openadlc:ignore` counts as shipped once GitHub says it closed as completed, read from `ignored_issues`, which the webhook and reconcile keep; closed for any other reason, open, or not found, it holds; reconcile looks up a dependency nothing has recorded, in a managed repository only
- [0021](0021-board-events-are-read-from-the-tables-they-happen-in.md): the board event feed behind `openadlc watch` (`GET /v1/board/events`) is polled from the tables events happen in (`tasks`, `gates`, `stage_moves`, the merge line, `pull.held` audit rows), from the database's now with a 10 s overlap deduplicated by event id, never emitted by writers; `GET /v1/board/tasks` is the live-task read behind `openadlc ls`
- [0022](0022-the-bridge-keeps-its-own-heartbeat-and-gap-report.md): the bridge beats into `bridge_heartbeat` every 30 s and twice on a clean shutdown (before its drains and at its end), on the database's clock; a start more than one beat after the last records one open gap report in `bridge_gaps`, merged and not stacked, with the tasks it resumed and the orphans one reconcile pass at start ended; a person dismisses it for everyone by its `backAt`; the live refresh probes the bridge before it refreshes and keeps the page under a banner when it gives no answer
- [0023](0023-a-wait-is-followed-to-its-root-in-both-reads.md): a waiting card's wait is followed to one root in both the board's read and the Needs-you read, from the same `readWaitFacts` and the same `followWaits`; a root names its Needs-you item by id, keeps person > dead > deep > self, and is stored nowhere
- [0024](0024-needs-you-alerts-are-raised-by-the-open-page.md): needs-you alerts (the tab's count and dot, a sound, a desktop notification) are raised by an open console tab from its live refresh, which keeps reading while hidden; the switches are per browser in `localStorage`, for every role; new is per document load, claimed across tabs; no service worker, push or bridge change
- [0025](0025-the-hosts-page-reads-what-reconcile-judges.md): Settings → Hosts (`GET /v1/hosts`, admin) judges a host `live`, `silent` or `never_seen` with reconcile's `HOST_SILENT_MS` rule on the bridge's clock; per-host load is `taskLoad`'s predicate grouped by `host_id`, with unclaimed queued tasks apart; what a silence cost is read from `tasks` (`exit_reason`, `ended_at >= last_seen_at`) and never stored; `hosts.cpus` and `memory_bytes` are what hostd saw at its last registration, null until reported
- [0026](0026-notifications-are-configured-in-settings-and-proved-by-their-last-send.md): where owner notifications go is `notifyTransport` in settings with its target (a Slack or webhook URL, or the ntfy topic) only in the `notify-target` secret, shown masked; each kind has a switch in `notifyKinds`; every send and test is a `notify.delivery` event; the `notifications` health check is a warning that reads the newest delivery since the transport was set and never sends; merge-waiting and review-stopped are read from Needs-you items every minute, once per `id@since`, with a baseline on an install's first look
- [0027](0027-the-board-by-state-is-grouped-in-the-console.md): the board by state is grouped in the console from the board and Needs-you reads, stored nowhere; a card takes the first fit of Needs you (a waiting work item, not `plan_change_waiting`, naming its ref, item key or pull request, or `gateOpen` without a held approval), Working, Waiting (anything else not Done) and Done today (since local midnight), and a Done card from before today is left out; `GET /v1/board` sends `repositories[].taskCapUsd`, the effective per-task cap
- [0028](0028-the-bridge-keeps-its-host-awake-while-work-is-in-flight.md): on macOS with `caffeinate`, the bridge holds one `caffeinate -i -w <pid>` while `inFlight()` counts a task queued or running, a merge updating, testing or merging and not held for a person to land, or a deploy waiting on a promote or running (merge and deploy rows untouched for 24 h left out), and lets go 60 s, on the monotonic clock, after the last tick that saw work; `keepAwake` `off` turns it off; a sleep is a wall gap over 120 s with wall minus monotonic over 60 s after a busy tick, judged even when that tick's read failed, recorded as a `bridge.slept` event and read by the history check `slept` for an hour
- [0029](0029-the-jump-list-is-read-whole-when-the-palette-opens.md): the command palette's item search is `GET /v1/items` (`user`), the open items and those closed in the last 30 days, at most 1000, read whole through `/api/palette` each time the palette opens and matched in the browser (`rankJump`); never held in `HeaderData`, never searched per keystroke; the console's key guards are `lib/keys.ts`
- [0030](0030-a-message-to-a-running-task-waits-in-its-inbox.md): a person's message to a role whose task is live (`queued`, or `running` on an engine that reports `takesMessages`; never `paused`) is a `task_inbox` row (migration 0160), `queued` then `taken` or `returned`, each by one `update … where state = 'queued' returning`; the task's runner pulls it with its task token before its first turn on every engine and at each complete turn boundary on one that takes messages, under a named `take_id`, and a take the bridge never answers fails the task with `releaseTake`; a row not taken is returned on the runner's `/state` and by a 30 s sweep, and goes through `MessageStarts.start` again; Claude and Codex take messages, Grok does not until its CLI is measured
- [0031](0031-a-design-memory-notice-is-raised-only-for-a-retire-or-a-retitle.md): a design memory supersede raises a Needs you card only for a pair whose new entry is absent (a retire) or has another title after trimming, collapsing spaces and lowercasing (`sameTitle`); the card is in the `system` group, dismissed for everyone through `acknowledgements` under `design-memory:<repo>#<issue>` by the event's `at` (`POST /v1/repos/:name/design-memory/notices/dismiss`, role `user`); the event carries `how` (`answered` or `unopposed`), which the card reads in place of the free-text `by`
- [0032](0032-person-roles-are-one-install-setting-filtered-by-humans.md): person roles are one install setting, `personRoles`, JSON `{roles:[{id, name?, members}]}`; Product, Legal and Engineering are constants in `packages/shared/src/people-roles.ts` whose names are never stored; a custom role's id is `pr_` and 8 hex, assigned once and kept across renames; every read shows only members among the live `humans`, and `PATCH /v1/install` prunes the stored setting when `humans` is saved (`people_roles.pruned`); `PUT /v1/people-roles` (admin) replaces the whole list (`people_roles.changed`) and is the only other writer
- [0033](0033-a-gate-stores-its-decision-and-consequences.md): a question's `decision` and `consequences` are columns on `gates` (migration 0161, `consequences text[] not null default '{}'`), read by every gate select in `threads.ts` and copied into the gate message's payload for the timeline; consequences are shown only when paired one to one with the final options (`parseQuestion` against the marker's options as written; `Gates.open`, the console and `renderGateComment` against the options they show), never for a plan change, and are display only: an answer resolves against `options` alone
- [0034](0034-one-list-of-people.md): an install's people are one table, `people` (migration 0162), keyed by a person id, with name, optional email, console role, GitHub login, `github_user_id` (the pin), `github_linked_at` (only the person's own link sets it) and `approves`; `users` and `person_github_accounts` are no longer read; `humans` is the logins of people with Approves on, else `OPENADLC_HUMANS`; person role members are person ids (superseding 0032's filter by `humans`); on GitHub anyone in People, matched by account id, answers a question, and only a plan change or the cost-cap question needs Approves; `gates.answered_by_person` records who answered either way
- [0035](0035-needs-you-items-follow-person-roles.md): on a cloud install a Needs-you item reaches only its audience, worked out on every read from People and roles (`needs-you-audience.ts`): a question's marker `role` (by name, kept on the gate by id), approvers for approvals, admins for the install's own cards, Engineering for the crew's; nobody falls back to everyone with why; `GET /v1/attention` is per viewer; a local install routes nothing; each person may set their own channel (`personNotify` and `notify-target:person:<id>`), and routed items skip the install's channel
- [0036](0036-a-person-decides-a-held-human-review-approval-from-the-console.md): a held Human-review approval (`approval:…`, `approve-again:…`) carries a `decision` (the issue's Outcome, why the person is asked, the crew's reviews recorded with `review.person_awaited`, the diff, and what each button does), and `GET /v1/attention` adds `yours` for the viewer; Approve is the person's own `APPROVE` review pinned to the head with `commit_id`, posted through ADR 0018's one-post token by the account linked to them, so `mergeDecision` is unchanged; Reject is an app comment, `pull.human_review_rejected` and `SendBack.reviewRound` with `by: '@login'`, once per head; Discuss is the item's message to the lead reviewer (or the builder) with `about`, audited as `pull.human_review_discussed`; the bridge refuses Approve and Reject unless the viewer's linked account id is the awaited login's and the head is the one they saw
- [0037](0037-a-person-merges-a-held-pull-request-from-the-console.md): a held merge (`merge:…`) carries `heldMerge` and a held promote (`promote:…`) `heldPromote`, each saying why it waits and what each button does; a console Merge is the person's own `PUT /pulls/{n}/merge` at the head they saw, through ADR 0018's one-post token, by a linked account GitHub lets write; `mergeBlockers` (`automation.ts`) lists every unmet merge rule with a kind, and the bridge merges only over `person` ones, checked at the press and at the code's approval, never over a required check, a crew review or a Human-review login; `mergeDecision` is unchanged, held to `mergeBlockers` by a parity test; Leave it and Keep holding are install-wide acknowledgements (`POST /v1/attention/leave`) until the head, reason or newest review, or the promote's sha, changes
- [0038](0038-a-late-request-for-changes-reopens-the-leads-decision.md): a non-lead seat asked on a pull request whose latest verdict on this diff is `request_changes`, given after the lead's latest review of it while the lead approves, holds `review-gate` (`reviewStanding.lateAsks`) and makes `leadDue` fire again with `since` that ask's time and an `asked-again.md` brief; "after" is `submittedAt`, falling back to review id; `mergeDecision` is unchanged and holds through the gate; no `review.stalled` while the lead is due
- [0039](0039-seat-trigger-labels-are-read-from-closing-issues.md): a seat's `trigger.labels` also match the labels of the issues a pull request closes in the same repository, read from GitHub on every decision (`Automation.closingIssueLabels`) and passed to `decideReviewers` as `issueLabels` by the opened path, the conflict re-check, `reviewStanding` and `mergeFacts`; only trigger labels are taken, kept apart from the pull request's own, which alone feed the fast path and scope; nothing is written to the pull request; the reason names the issue; an unreadable issue counts as unlabelled and holds nothing
- [0040](0040-a-merged-dependency-counts-where-the-repository-ships-by-release.md): `dependencyIsSatisfied(dependency, ignored, { shipsByRelease })` takes the third argument at every caller (the dispatcher's unblock pass and lease check, `waitingOf`, stacking, `StageHandoff.markReadiness`); stage `merged`, not abandoned, counts where the dependency's own repository ships by release, read through `DeliveryKnowledge` by `releaseShipping` (a read error, a throw or an unmanaged repository answers no); Done still waits for the release; a `blocked`, not ignored issue whose Dependencies name nothing is unblocked with `dependencies: []`; amends ADR 0013's "`dependencyIsSatisfied` is unchanged"
- [0041](0041-a-stacked-pull-request-is-brought-up-to-date-when-its-base-merges.md): the bridge merges the default branch into a stacked pull request's branch with `MergeLine.updateStacked` (the line's `stackedUpdate`, in its per-repository queue) when its dependency merges into the default branch, at a held one's let-go, and before the first round of one opened or pushed by its builder with a local CI pass after the dependency shipped; `stack.updating` carries `carry` (absent reads true): true keeps the approvals across the update (`stack.updated`), false opens the round on the merged head; a conflict opens the resolution round, the only time a builder is started; a branch already up to date, a held one, one under a running build or patch round, and an unreadable stack are left alone
- [0042](0042-a-conflicting-head-is-resolved-before-review.md): on an issue's pull request, the review start reads mergeability once (`mergeabilityOf`: `mergeable: false` or `dirty` conflicts; null with `unknown` or no state is unknown), except for the line's update and a lead-only resolution; a conflicting head asks no seat and opens `ConflictRounds.start({ beforeReview: true })`, always a full review after and `FULL_REVIEW_WHY.beforeReview`, no `maxRounds` round; unknown is held off the delivery by `MergeabilityWait`, re-read every 5 s, reviews start at 60 s, recorded as `review.mergeability_waiting`/`_decided` and resumed at start-up; a round waiting on a busy builder starts through the `StageRunner`; every patch round on a conflicting pull request gets `conflict.md`
