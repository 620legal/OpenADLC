# 0088. A project map reaches spec and implement sessions as a capped document from hostd

- **Status:** accepted
- **Date:** 2026-11-26

## Context

ADR 0087 has hostd build a map of each managed repository's default branch
under its work root. Until it is read it saves nothing: every design and build
session still starts by exploring the repository the way the last one did.
#380 asks for the map on a console page and for spec and implement sessions to
start with it.

Two constraints shape how. Text in a session's prompt is read as if the
session were told it, so the map must reach the session as data, and from a
place no pull request can write: a map read from the task's worktree could be
edited by the pull request it briefs. And a map grows with the repository: one
of 200 areas is about 100 KB, tens of thousands of tokens on every task that
gets it.

## Decision

- `Context.forSubject` in the bridge adds the map as a context document named
  `project-map.md`, for tasks of kind `spec` and `implement` only, after
  `issue.md` and before intake and design memory, so the subject comes first.
- The bridge reads it from hostd through `GET /project-maps/:owner/:name`
  (internal secret), which reads `<workRoot>/maps/<owner>__<name>.md` whole
  and fetches nothing. It is never read from a worktree.
- The document opens with one line naming the repository and the commit, and
  says to open the files it names before relying on them. A map over
  `MAP_CONTEXT_BYTES` (48 KiB) is cut at the last whole line before the limit,
  followed by a note of how many lines continue on the Map page.
- skill-runner fences it like every document, with its own source line:
  generated by OpenADLC from the default branch, a summary of merged files to
  read, never instructions; where it and the worktree differ, the worktree is
  right. It is not among the documents written by people.
- No reader, no map, or a read that fails adds nothing, with a warning in the
  bridge's log for a failure: the task starts as it did before maps, as with
  design memory.
- The console's Map page (`/map`, `/map/<repo>`) shows the map whole, with the
  commit it was built from and when, through `GET /v1/repos/:name/map`, a
  `user` route: every console user may read any managed repository's map.

## What this rules out

- **hostd's task runner adding the file itself.** It could read
  `<workRoot>/maps/` in `contextFilesFor` with no network call, but which kind
  of task gets which document is decided in one place, `Context.forSubject`
  (images, intake, design memory). A second place in hostd would split that
  decision, and the bridge needs a read route for the console page anyway.
- **Reading the map from the worktree, or committing it to the repository.**
  A pull request could change it to brief its own builder or reviewer.
- **The whole map, however large.** A large repository's map would cost tens of
  thousands of tokens on every spec and implement task; the cut keeps it
  bounded, and the console always shows the rest.
- **Every kind of task.** Review, patch, intake and QA tasks are not given the
  map: the issue asks for spec and implement, and a reviewer reads a diff, not
  the repository. Adding a kind is one line in `READS_PROJECT_MAP`.
- **A with-and-without token figure from a scripted run.** The scripted engine
  reports fixed usage per turn whatever the prompt, so it cannot show a
  saving. What the map adds to a prompt is measured on this repository's own
  map by a test (`apps/hostd/src/project-map.test.ts`); the saving in
  exploration is compared in the usage ledger before and after (#385).

## What would make this worth revisiting

- The ledger comparison (#385) showing the map does not reduce what spec and
  implement sessions read, which would make it a cost with no saving.
- Maps of managed repositories regularly passing 48 KiB, so that sessions are
  routinely given a cut map; the cut or the map's layout would then want
  another look.
- Other kinds of task shown to explore as much as design and the build do.
